# AIS storage reduction implementation plan

This plan implements the design in [AIS storage reduction plan](AIS_STORAGE_REDUCTION_PLAN.md) in four phases. The study covers 30 AIS dates across New York/New Jersey, Los Angeles, and Houston. Use decimal units for the provisional limits: 10 GB for retained output, 2 GB for cached responses, and a separate scratch allowance measured on Ubuntu. The retained limit averages about 333 MB per date across all three ports, including database indexes and study metadata.

## Phase 1 — Establish the baseline and trim duplicate reports

1. On the Ubuntu host, inventory retained reports, cache, logs, and scratch separately. Record apparent file sizes by date, port, and file type. Also track actual filesystem usage and peak free-space drawdown during a run. Include adjacent-day downloads, staging, and partial files. Save the baseline measurements outside the repository.
2. Choose at least three pilot dates that together cover busy Houston traffic, overlapping replay windows, and a UTC midnight crossing. Capture legacy counts, scores, replay outputs, and missing environmental data for all three ports. Record source URLs and checksums so later comparisons use the same inputs.
3. In [the historical runner](run_historical_near_miss_study.py), add an opt-in compact mode that sends detector and evidence intermediates to the work directory and skips persistent aggregate candidate CSV copies. Keep the per-port score data needed for reports and legacy replay until the SQLite and dashboard phases pass. Stage publication on the report filesystem and publish a date only after all three ports succeed. Verify scratch is cleaned after success and that an interrupted attempt can be retried.
4. Configure explicit start and end dates in [the cron wrapper](run_cron.sh) for the study. Check the NOAA index for gaps before approving the range, and count completed AIS dates separately from cron invocations. Use a separate report directory for the pilot so the current run configuration and existing reports stay intact.

**Exit gate.** Legacy and compact pilot outputs agree on screening and review totals, displayed encounter scores, and replays. Record the measured savings and peak scratch use by filesystem. Leave compact mode opt-in until Phase 4.

## Phase 2 — Store each completed date in SQLite

1. Add a schema-versioned store using Python's `sqlite3`. Store daily and per-port totals, retained encounters and evidence, vessel identities and names, encounter-to-vessel membership and replay bounds, track samples, hourly traffic and environmental observations, and source provenance. Keep stable encounter IDs across retries and migration. Carry over the existing exclusion and score rules. Capture the CSV/HTML exporter and Node viewer eligibility rules separately because they currently filter at different points.
2. In [the replay exporter](ais_event_dashboard.py), separate data selection from file writing so the legacy exporter and compact writer share the same inputs and rules. Store samples once per port and UTC source date for the union of retained replay windows. Preserve distinct samples at the same timestamp and the vessel names used in the legacy replay. Keep first-flag and closest-approach times, nearby anchored vessel membership, and the environmental hour and direction conventions. Use the original coordinate precision in the pilot.
3. Commit all three ports and the date completion record in one transaction. Use a single writer and have readers expose only committed dates. Reconcile run state from committed records on restart so a crash after commit can refresh progress without duplicating rows. Record missing adjacent-day AIS and environmental coverage explicitly. Retain AIS checksums, source URLs, port bounds, and the scoring version in the store.
4. Before downloading, check the retained size and reserve measured headroom on each relevant filesystem for scratch, the next date, and SQLite journal or WAL growth. Check size again before publishing and leave a date pending if it cannot fit. Count SQLite sidecars and retained metadata in the budget. Bound cached response bodies at 2 GB in [the environmental downloader](ais_environment.py) and related cache paths. Reuse historical responses where their freshness rules permit, evict the oldest unused entries, and keep [API cooldown state](ais_request_policy.py) outside eviction. Rotate verbose logs while retaining compact run outcomes.

**Exit gate.** On the pilot, compare scores, exclusion and review totals, sample counts and positions, vessel labels, window bounds, hourly values, and missing-data behavior. Simulate a failure before commit, a failure immediately after commit, a retry, and insufficient disk space. Verify that each date appears at most once, counts agree with its completed ports, and the preflight disk check can stop a download.

## Phase 3 — Load dashboard data and CSV exports on demand

1. Keep the [Node dashboard server](ais_dashboard_server.js) and its local routes. Add a small shared shell and read-only endpoints for progress, a paged date-and-port encounter list, one encounter replay, and filtered CSV exports. Confirm the Ubuntu Node runtime first. The [current setup](README.md) supports Node.js 18, so use a Python `sqlite3` reader if the deployed Node lacks a suitable built-in reader. Keep legacy report folders readable during the pilot.
2. Fetch only the selected encounter's vessels, bounded tracks, and replay hours. Resolve cross-midnight windows by UTC source date and time, including samples available only from the adjacent AIS download. Retain the current playback and zoom controls, vessel names, first-flag and closest-approach displays, traffic counts, wind and current arrows, and wave height. Preserve the visible distinction between zero and missing values.
3. Build progress from committed date records and keep it available while cron is writing. Stream requested CSV rows by date, port, or encounter. Offer gzip for larger extracts and avoid writing expanded export copies to the report directory.

**Exit gate.** Compare the legacy and compact dashboards on all pilot dates, including a midnight replay and an encounter with missing observations. Check that an empty day renders, the progress page and encounter list responses carry no track samples, and selecting a replay fetches only that encounter's data. Compare filtered CSV rows against the pilot output. Run `python -m unittest discover` and `node --check ais_dashboard_server.js` before rollout.

## Phase 4 — Verify the budget and switch cron

1. Report actual retained growth per date across all three ports, peak scratch usage, and peak cache size. Project 30 dates using both the pilot average and the busiest measured date. Include SQLite indexes and sidecars, metadata, and retained logs. If the projection exceeds 10 GB, profile the largest tables and test lossless packing or compression before proposing changes to sampling or precision.
2. Once the pilot passes, point cron and the dashboard to a fresh compact report directory. Keep the existing lock and request pacing. Verify the first scheduled publication and confirm that the study stops after the agreed 30 dates, with any gaps visible on the progress page. Keep the legacy report directory available for rollback.
3. Migrate historical output separately if needed. Import and verify one date at a time against the legacy summaries and replay files, including dates with zero retained encounters. Use another volume if the old and new copies cannot fit together. Decide whether to keep an audit archive before removing verified legacy copies.

**Exit gate.** The 30-date run completes within the retained and cache limits, and measured scratch usage fits the Ubuntu host. The latest progress page and a selected replay open with the full study in place. Record actual totals and any verified migration dates.
